# Digital certificates and certification authorities

- Document: c11 (course)
- Source: Written for this project from the topics of the CoSc4035 Computer Security course slides (Jimma University), Chapter 3, part 2
- Licence: CC BY 4.0

Public-key cryptography solves part of the key distribution problem, but it raises a new question: how can Bob be sure that a public key really belongs to Alice and not to an attacker? Without an answer, a simple key exchange is open to a man-in-the-middle attack. Suppose A sends her public key to B without protection. An attacker E intercepts it and sends B his own public key instead. B encrypts a new session key with E's public key, E decrypts it, encrypts it again with A's public key and passes it on to A. A and B now share a session key, but E knows it too and can read everything they send. The Diffie-Hellman key agreement method has the same weakness.

The solution is a trusted third party called a certification authority (CA). A certificate binds a public key to its owner. It contains the owner's public key, the owner's identifier and a validity period, and the whole block is signed with the CA's private key. Anyone who has the CA's public key can check the signature. If the check succeeds, it proves both that the certificate is genuine and that the public key belongs to the named owner. Two parties can exchange certificates in this way to obtain each other's authenticated public keys, and then use those keys to agree on a secret session key. For extra safety, a party can also ask the CA whether a certificate has been revoked.

The set of standards for creating, managing, storing, distributing and revoking certificates is called a public key infrastructure (PKI). X.509, described in RFC 5280, is the PKI standard that defines the certificate format. Its fields include the version number, a serial number assigned by the CA, the signature algorithm, the issuer (the name of the CA), the validity period, the subject (the person or organisation the certificate was issued to) and the subject's public key. X.509 uses a strict hierarchy of CAs in which trust flows only downwards: the CAs at the top are called root CAs, and those below them are intermediate CAs.
