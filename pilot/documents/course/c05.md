# Time-of-check to time-of-use errors

- Document: c05 (course)
- Source: Written for this project from the topics of the CoSc4035 Computer Security course slides (Jimma University), Chapter 2
- Licence: CC BY 4.0

A time-of-check to time-of-use (TOCTTOU) error, also called a race condition, can occur whenever a system checks permission for an action and then performs the action in a separate step. The usual sequence is:
1. A user asks the system to do something.
2. The system checks that the user is allowed to do it.
3. The system does it.
If the situation can change between step 2 and step 3, an attacker can get the system to check one thing and then act on something else.

A classic example comes from Unix. A terminal program runs with superuser privileges (it is setuid) because allocating terminals to users is a privileged operation. The program also lets users save the contents of their terminal to a log file. Before opening the file, it checks whether the user is allowed to write to it. The attacker creates a symbolic link named logfile that points to a file she owns, so the permission check succeeds. In the short time between the check and the opening of the file, she changes the link so that logfile points to /etc/passwd. The program, still running as superuser, then writes into the password file. The name was the same at both moments, but the file behind the name was not.

This is a failure of access control, and it can damage confidentiality, integrity, or both. The defences are:
- When acting on behalf of someone else, make sure that everything the access decision depends on stays the same between the check and the action.
- Keep a private copy of the request, so that it cannot be changed after the check.
- Act on the object itself rather than through a level of indirection such as a file name or a link.
- If that is not possible, lock the object so that it cannot change between the check and the use.
