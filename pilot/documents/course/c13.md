# TCP SYN flood and ARP spoofing

- Document: c13 (course)
- Source: Written for this project from the topics of the CoSc4035 Computer Security course slides (Jimma University), Chapter 4
- Licence: CC BY 4.0

Many Internet protocols were designed for a small group of users who trusted each other, so they include no defences against attackers. Two well-known examples of attacks that exploit this are the TCP SYN flood and ARP spoofing.

A normal TCP connection starts with a three-way handshake. The client sends a SYN message to ask for a connection, the server answers with a SYN-ACK, and the client replies with an ACK, after which the connection is open. In a SYN flood, a type of denial-of-service attack, the attacker sends a large number of SYN messages, often from fake IP addresses, faster than the server can handle them. The server answers each one with a SYN-ACK and keeps resources reserved while it waits for the final ACK. The ACK never comes, either because the attacker does not send it or because the SYN-ACK went to a spoofed address. The server's resources fill up, and it stops responding to real users.

ARP (the Address Resolution Protocol) works on the local network. A computer that knows another computer's IP address but needs its MAC (Ethernet) address broadcasts a request, and the owner of that IP address replies with its MAC address. In ARP spoofing, also called ARP cache poisoning, the attacker sends fake ARP replies that link the attacker's MAC address to the IP address of another host, usually the default gateway. Traffic meant for that host then goes to the attacker, who can read it, change it or stop it. ARP spoofing is often the first step of other attacks, such as man-in-the-middle, session hijacking or denial of service.

The attack works because ARP is a stateless protocol. Hosts store any ARP reply they receive, even if they never sent a request, and a new reply overwrites an existing entry even if that entry has not expired. ARP also gives a host no way to check who sent a reply.
